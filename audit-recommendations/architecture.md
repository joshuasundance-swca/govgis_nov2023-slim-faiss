# ARCHITECTURE: Target module decomposition soundness for this app's actual size

## Assessment

The 9/10-file decomposition (`app.py` + `govgis/{config,models,artifacts,retrieval,presentation,providers/{base,anthropic,openai,huggingface}}.py`) is right-sized for a retrieval-first app with strict-typing/XSS requirements and three optional LLM providers behind a shared protocol — it is neither a rewrite-for-rewrite's-sake over-engineering of a ~250-line app nor an under-engineered flat script, given the plan's own critical trust-boundary and prompt-injection risk sections justify the separation. The current monolith (`app.py`) mixes UI, retrieval, unsafe rendering (`st.components.v1.html` on raw dataset content, `app.py:225-227`), and provider calls in one file — precisely the coupling the plan's risk sections identify as needing separation, and the `providers/base.py` + per-provider file split is a concrete, well-justified home for the plan's own principle that "provider-specific capabilities should not leak into the common interface without a tested need." The one concrete problem found is a seam gap rather than a module-count problem: the pipeline names a "safe presentation model" as a distinct stage, but neither `models.py`'s described contents nor `presentation.py`'s described contents actually name or own that type — a real coherence hole in exactly the security boundary the plan is trying to close, though one already partially covered by Stage 3's existing browser-level XSS gate and its "no `gr.HTML` on dataset/user/model content" rule, so the gap is a static-enforcement strengthening opportunity rather than an unguarded hole.

### ARCHITECTURE-01. "Safe presentation model" is a named pipeline stage but no module owns its type, risking silent reintroduction of the current XSS bug's root cause

**Severity**: Medium · **Effort**: S · **Location**: `docs/modernization-plan.md`, section "Target architecture" (pipeline diagram, lines 170-178; module list, lines 180-192)

**Evidence**: The pipeline diagram reads: `... -> typed GIS search results -> optional provider-neutral query rewrite or answer synthesis -> safe presentation model -> sanitized rendered output`. `govgis/models.py` is described only as "Pydantic request, GIS record, result, and provider models" (line 184) — no presentation model is listed. `govgis/presentation.py` is described only by operation — "plain-text conversion, link validation, and escaped Markdown" (lines 191-192) — never as returning a distinct typed model. Stage 3's gate says "render only validated presentation models" (line 335) without naming the type or its owning module. The current app's XSS root cause is exactly this shape: `app.py:225-227` calls `st.components.v1.html(data.get("description", missing_value))` directly on untrusted, dataset-controlled content because nothing forced an intermediate sanitization/typing step.

**Why it matters**: There is no stated type that statically distinguishes "raw GIS record" from "safe-to-render presentation record." Without a named `PresentationRecord`-style type in `models.py`, a future edit to the deliberately thin `app.py` could render a `GISRecord`/result field directly (bypassing `presentation.py`) with no type checker or code-review signal catching it — reopening the same class of vulnerability the plan's "Unsafe rendering" section calls a critical trust boundary. This is not an unguarded hole: Stage 3 already carries a runtime browser-level gate ("scripts and unsafe links do not execute," lines 339-340) and an explicit rule against `gr.HTML` on dataset/user/model content (line 136). The gap is that the boundary is enforced only at runtime/browser-test time, not at compile time or in code review, and the plan's own module contract doesn't name the type its own pipeline diagram and Stage 3 gate both refer to.

**Recommendation**: Reframe as a defense-in-depth / static-enforcement tightening rather than a gap-fill, tied to the plan's existing mypy gate. Concretely: (1) add a distinct type (e.g. `PresentationRecord`) to `govgis/models.py`'s described contents; (2) state that `govgis/presentation.py` is the only producer of it; (3) state that `app.py` may render only that type, never raw `GISRecord`/result/provider models; (4) revise Stage 3's gate from the implicit "render only validated presentation models" to name the type explicitly and note that `app.py`'s render function is typed to accept only `PresentationRecord`, so the existing mypy step (central quality gate, line 438 / Stage 1 gate) statically enforces the boundary. This turns a runtime-only browser check into a compile-time + review-time signal without conflicting with any Confirmed decision or other stage gate.

## Minor notes (not adversarially verified)

- **Provider-per-file split is well-justified, not over-engineering.** `govgis/providers/base.py` ("narrow provider protocol and common errors") is a concrete, named home for the plan's own principle "Provider-specific capabilities should not leak into the common interface without a tested need" (section "Optional answer synthesis"). Given three genuinely different SDKs (Anthropic Messages, OpenAI Responses, HF `InferenceClient`) and BYOK/OAuth handling that differs per provider, splitting them into `anthropic.py`/`openai.py`/`huggingface.py` behind one protocol is right-sized, not excessive, for this app. No change recommended.

- **Overall module count is reasonable for the stated feature surface.** 10 files (`app.py` + 9 under `govgis/`) for retrieval + strict typed presentation (XSS-critical) + 3-provider optional generation is proportionate, not over-engineered — the current ~250-line monolith mixes UI, retrieval, unsafe rendering, and provider calls in one file, which is precisely the coupling the plan's own risk sections (unsafe rendering, prompt injection, provider errors) identify as needing separation. The gap found above is about a missing seam, not an excess one.
