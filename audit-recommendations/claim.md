### CLAIM-01. No required PR check exists to attach Stage 6's merge gate to

**Severity**: Medium · **Effort**: S · **Location**: docs/modernization-plan.md, section "Reliability and observability gaps" (line 163; also Stage 6 "merge only after required checks pass", line 396)

**Evidence**: Plan text: "The current required PR check only enforces a file-size limit." Stage 6 action: "merge only after required checks pass." Live check (re-run independently this audit): `gh api repos/joshuasundance-swca/govgis_nov2023-slim-faiss/branches/main/protection` returns HTTP 404 "Branch not protected." `.github/workflows/check-file-size-limit.yml` runs `on: pull_request` but is not configured as a required status check anywhere in the repo — there is no branch-protection object to hold that configuration. I confirmed the plan never mentions configuring branch protection anywhere (Stage 1, line 293, only makes CI *run* the gate, not *require* it).

**Why it matters**: The plan's own wording ("required PR check") is inaccurate — no check is actually required today; the file-size workflow runs but cannot block a merge. Stage 6's gate "merge only after required checks pass" has no enforcement mechanism to attach to, so as written it depends entirely on human discipline, not an executable gate — directly contradicting the plan's own stated principle that "unit-test success is not a proxy" and that gates must be observable/enforced. The stakes are real: `hf-space.yml` auto-deploys on push to main, so an unblocked merge auto-ships to the public Space.

**Recommendation**: Two-part revision. (1) Correct the "Reconciled baseline" wording at modernization-plan.md line 163: replace "The current required PR check only enforces a file-size limit" with an accurate statement that main has NO required status check today (live: branches/main/protection returns 404 "Branch not protected"); the file-size workflow runs on pull_request but cannot block a merge. (2) Add a concrete action making Stage 6's "merge only after required checks pass" enforceable: after Stage 1 lands the CI gate (pytest/ruff/mypy/pre-commit), configure GitHub branch protection on main requiring those check(s) to pass before merge, and record the exact required-check names once created. Sequence this as a post-Stage-1 action (not pre-Stage-1), since you cannot mark checks required before they exist. Optionally note the added stake: hf-space.yml auto-deploys on push to main, so an unblocked merge auto-ships to the public Space.

### CLAIM-02. "storage: null" claim doesn't match the live Space API's actual schema

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Reconciled baseline" (line 62)

**Evidence**: Plan text: "The Space API reported `storage: null` and did not expose a `volumes` field." Live check (independently reconfirmed this audit): `GET https://huggingface.co/api/spaces/joshuasundance/govgis_nov2023-slim-faiss` returns top-level keys `[_id, author, cardData, createdAt, datasets, disabled, gated, host, id, lastModified, likes, models, private, runtime, sdk, sha, siblings, subdomain, tags, usedStorage]` — no `storage` key at all (top-level or nested in `runtime`), and instead exposes `usedStorage: 0`. No `volumes` field either. This matches coordinator-verified-literals.md's candidate finding exactly.

**Why it matters**: Minor evidence-precision issue only — the substantive conclusion (no persistent storage configured) is still correct — but a maintainer re-verifying this claim against the live API in the future would find the described response shape doesn't exist, undermining trust in the reconciled-baseline section's precision.

**Recommendation**: Reword plan line 62 to match the current API schema, e.g.: "The Space API's JSON has no top-level `storage` key (it exposes `usedStorage: 0`) and no `volumes` field, consistent with HF docs that legacy persistent Space storage is no longer offered." Optionally add a one-clause note that the substantive conclusion (no persistent storage configured) is unchanged, so the correction reads as a precision fix rather than a reversal. Keep it aligned with line 234's existing wording.

### CLAIM-03. Streamlit-SDK "deprecated" claim cites a page with no deprecation language; the real evidence is uncited

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Confirmed decisions" (#1, lines 27-28) and "Evidence sources" ("Streamlit SDK deprecation", lines 451-452)

**Evidence**: Plan text: "Migrate the UI from the deprecated built-in Streamlit Space SDK to the native Gradio Space SDK," cited to `<https://huggingface.co/docs/hub/main/spaces-sdks-streamlit>`. Coordinator-verified-literals.md (accepted without re-fetching per instructions, corroborated by the plan's own "Evidence sources" list already containing a separate, uncited `spaces-config-reference` link at line 450) found that page is a live undated tutorial with no deprecation notice, while the actual smoking gun is `spaces-config-reference`'s enumeration of valid `sdk` values as only `gradio`, `docker`, or `static` — Streamlit is silently absent from that list, not flagged as deprecated-with-notice.

**Why it matters**: The plan's strongest baseline justification for the Gradio migration decision cites the weaker of two available pieces of evidence. If a maintainer clicks through to verify "deprecated" before Stage 1, they will find a page that doesn't say that, which could cast unwarranted doubt on a well-founded decision (the migration itself is still correct — Streamlit genuinely is absent from the current valid-SDK list, and the production Space's `sdk: streamlit` config is only running because it's grandfathered).

**Recommendation**: Re-point the Streamlit citation to the evidence that actually supports it. `spaces-config-reference` is ALREADY in the Evidence sources list (line 450, currently labeled "Hugging Face Space configuration") and its `sdk` enumeration (`gradio`/`docker`/`static`, Streamlit absent) is the real support for the claim — so relabel/cross-reference that existing entry against the Streamlit line rather than "adding" it, and either drop or demote the `spaces-sdks-streamlit` tutorial link (which carries no deprecation language). Then soften decision #1's "deprecated built-in Streamlit Space SDK" to something evidence-matched, e.g. "no longer offered/documented as a configurable SDK for new or reconfigured Spaces (absent from the current `sdk` value enumeration; the production Space's `sdk: streamlit` continues to run only because it predates that change)." Optionally record it as a one-line open note that no formal dated HF deprecation announcement was located, only the enum-absence.

### CLAIM-04. "Recovery implementation commit: 3e85082" is tree-identical to the deployed SHA 5b3caca, not a distinct fallback state

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Reconciled baseline" ("Known-good rollback points", lines 68-73)

**Evidence**: Plan text lists two separate bullets: "GitHub and Space revision: `5b3cacaf27fc4c75cb4e6e4c3d86dc1796ece5c9`" and "Recovery implementation commit: `3e85082`." Live check (re-run independently this audit): `git rev-parse 3e85082^{tree}` and `git rev-parse 5b3caca^{tree}` both return `7bf67a91a3b207eb8618cbf5ffa9a07eb688668f` — identical trees. `git diff 3e85082 5b3caca --stat` produces zero output. `git rev-list --parents -n 1 5b3caca` confirms `5b3caca` is a merge commit with parents `407ebb1` and `3e85082` — i.e. the PR #46 merge added no file changes beyond `3e85082`'s own content. Separately, I confirmed via `git show 3e85082` that this commit is the one that removed the stale `streamlit==1.31.0` pin from requirements.txt and added `tests/test_space_build_contract.py` — real, meaningful implementation content, just tree-identical to the merge that carries it into main.

**Why it matters**: Presented as two entries under "Known-good rollback points" without noting they are content-identical, a maintainer executing Stage 0's "document the exact rollback command" could reasonably wonder which of the two SHAs to target, or assume `3e85082` represents an earlier/different known-good state to fall back to if `5b3caca` were somehow bad. It does not — restoring either SHA produces the exact same working tree.

**Recommendation**: Keep the "3e85082" bullet but append a clarifying clause, e.g. "Recovery implementation commit: 3e85082 (tree-identical to 5b3caca; the PR #46 merge added no further changes)." This preserves the implementation-provenance note while removing the ambiguity about which SHA a rollback command should target. Do not simply drop the bullet — the clause is more useful, and it aligns with Stage 5's existing rollback wording (line 390) which already targets 5b3caca as canonical.
