# GATES: Validation-gate coverage across the 8 implementation stages

## Assessment

Gate coverage across the 8 stages is generally strong where the plan describes a concrete artifact (browser tests, checksum scripts, CI logs, SHA verification) — Stages 1, 3, 5, and 6 each have Gate bullets that are genuinely executable and map closely to their Actions, and the Central quality gate block is a real, runnable command sequence that later stages correctly layer on top of rather than duplicate. The gaps cluster around three repeatable patterns: (1) a Gate bullet references a decision or threshold ("the agreed threshold," "the predeclared quality floor") that the document's own "Open implementation-time questions" section still lists as unresolved — the open-question status has quietly become load-bearing in Stage 2 and Stage 7 without being re-flagged, which is exactly the trap the audit's constitution rule (c) describes; (2) an Action that requires a judgment call under measurement (Stage 4's provider/model default decision) has zero corresponding Gate bullet, so a wrong call is architecturally invisible until it ships — the same failure class that let `claude-instant-v1`/`claude-2.1` sit hard-coded in app.py past their retirement dates; (3) the Rollback subsections are structurally inconsistent: Stage 0 and Stage 7 have none at all (every other stage has one), and Stage 3's is a single non-actionable sentence next to a 3-bullet Gate. A smaller, mechanism-level gap sits in Stage 0: it demands cold-start/RSS/latency capture but its Gate doesn't require the capture mechanism to actually work, even though the Reconciled Baseline section already proves the obvious mechanism (public logs) returns 401.

### GATES-01. Stage 2 and Stage 7 gates assume a retrieval-quality threshold the document's own Open Questions section says is still undecided

**Severity**: Medium · **Effort**: S · **Location**: docs/modernization-plan.md, sections "Stage 2: safe artifact conversion and retrieval core" (Gate), "Stage 7: evaluated footprint reduction" (Gate), and "Open implementation-time questions"

**Evidence**: Stage 2 Gate: "baseline retrieval quality meets the agreed threshold;" Stage 7 Gate: "ship a smaller representation only if it meets the predeclared quality floor." Yet "Open implementation-time questions" still lists: "What retrieval-quality threshold and query set should govern index changes?" as open. No other section of the document states a numeric or procedural definition of this threshold/floor.

**Why it matters**: Both gates are unexecutable as literally written — there is no recorded value or query set to compare against. In practice this means the go/no-go call at Stage 2 (does the new direct-FAISS retrieval core match the legacy LangChain retriever well enough to proceed) and at Stage 7 (does a footprint-reduced index still meet quality bar before shipping to the public Space) will be made ad hoc at implementation time rather than against a predeclared, auditable number — defeating the stated purpose of "predeclared."

**Recommendation**: Prefer option (b): keep the threshold open until Stage 0 produces real numbers, but (1) change the Stage 2 and Stage 7 gate bullets so they no longer read as if the value already exists — e.g. Stage 2: "baseline retrieval quality meets the threshold recorded in Stage 0 (TBD until the oracle set runs)"; Stage 7: "meets the same recorded quality floor," and (2) add "record the retrieval-quality threshold (and bind it to the Stage 0 query set)" to Stage 0's Actions AND its Gate outputs, since Stage 0 already builds the 15-25 query set but currently never records a threshold. This gives Stage 2/7 a concrete inherited artifact. Note also that Stage 2 already carries the more concrete adjacent concept "retrieval parity" (verify new direct-FAISS matches legacy on the oracle set) as its action — the gate can lean on parity as the executable Stage-2 go/no-go while the absolute quality floor primarily governs Stage 7's shrink decision.

### GATES-02. Stage 4's provider/model-default decision has no corresponding Gate bullet at all

**Severity**: Medium · **Effort**: S · **Location**: docs/modernization-plan.md, section "Stage 4: providers and authentication" (Actions vs. Gate)

**Evidence**: Actions includes: "decide provider/model defaults from representative quality, cost, and latency measurements." The Gate section for the same stage has exactly four bullets: "provider contract tests pass with recorded fixtures or mocks; opt-in live smoke tests pass without exposing credentials; retrieval survives every provider failure; HF calls are attributed to the signed-in user, not the Space owner." None of these touch quality, cost, or latency, or validate that the measurement-driven decision process actually happened or produced a defensible choice.

**Why it matters**: A wrong default model (too expensive, too slow, or simply a lower-quality tier chosen without real comparison) would pass every stated Gate and ship to the public Space undetected — structurally the same failure mode that let app.py hard-code `claude-instant-v1`/`claude-2.1` (both now retired per the Anthropic model-deprecations page) with no gate ever catching it.

**Recommendation**: Add a Stage 4 Gate bullet requiring a recorded, script-generated provider/model comparison (retrieval-answer quality score, p50/p95 latency, and per-model cost-per-1k-tokens as user-facing guidance) across the candidate models before any default is set, with the raw table checked into the repo alongside the Stage 0 oracle outputs so the decision is auditable rather than asserted in prose. This mirrors the plan's own established measurement-gate pattern (Stage 0 "raw outputs retained", Stage 2 quality threshold, Stage 7 predeclared quality floor). Frame cost as informational since Anthropic/OpenAI are BYOK (user-borne) and HF uses the signed-in user's token; keep quality and latency as the load-bearing axes.

### GATES-03. Stage 0 and Stage 7 have no Rollback subsection at all; Stage 3's Rollback is far vaguer than its Gate

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, sections "Stage 0: baseline and test oracle", "Stage 3: Gradio and secure presentation" (Rollback), and "Stage 7: evaluated footprint reduction"

**Evidence**: Stage 0 goes directly from its Gate's last bullet ("the current production Space remains unchanged.") to the "### Stage 1" heading — no Rollback subsection. Stage 7 goes directly from its Gate's last bullet ("ship a smaller representation only if it meets the predeclared quality floor.") to "## Central quality gate" — also no Rollback subsection. Every other stage (1, 2, 4, 5, 6) has one. Stage 3's Rollback reads in full: "staging only until this and provider gates pass." against a 3-bullet Gate ("browser-level tests prove scripts and unsafe links do not execute; local Gradio API and browser smoke tests pass; required GIS fields and links are visible and usable.").

**Why it matters**: Stage 7 in particular authorizes shipping a changed retrieval representation to the production-facing index after a footprint-reduction benchmark; having no stated rollback step for that specific stage (versus relying implicitly on Stage 6's generic redeploy-known-good procedure) is an inconsistency a future implementer could read as "no rollback needed here." Stage 3's one-line Rollback gives no concrete recovery action (unlike Stage 2's "keep legacy production at its known-good SHA; do not deploy this stage alone" or Stage 6's explicit redeploy-and-verify procedure).

**Recommendation**: Add a one-line Rollback subsection to Stage 7 (the valuable part): e.g. "revert to the Stage 6 shipped artifact/manifest revision and redeploy; do not delete the prior artifact until the new one clears the observation window." This closes a genuine gap since Stage 7 uses the word "ship" for a changed retrieval representation reaching production yet states no rollback. Treat the Stage 0 and Stage 3 changes as optional-cosmetic, not required: Stage 0 performs no deployment (test-oracle/baseline/tagging only) and its Gate already states "production remains unchanged," so a "no rollback needed" line is pure template symmetry; Stage 3 never reaches production, so its "staging only until gates pass" is an adequate containment rollback in the same genre as Stages 1/2/4 — if tightened at all, name "keep production on 5b3caca; this stays in staging," but it is not a defect.

### GATES-04. Stage 0's metrics-capture Gate doesn't require the capture mechanism to actually work, despite the plan already knowing the obvious mechanism is blocked

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, sections "Stage 0: baseline and test oracle" (Actions/Gate), "Reconciled baseline", and "Startup and storage strategy"

**Evidence**: Stage 0 Actions: "capture cold-start, artifact-load, RSS, first-query, warm-query, and provider latency;" Stage 0 Gate: "baseline data and counts are generated by scripts; raw outputs are retained for review; the current production Space remains unchanged." Meanwhile "Reconciled baseline" states: "Public build and run log endpoints returned HTTP 401. Build duration, artifact-load duration, peak RSS, and cold-start time are therefore UNVERIFIED." The only stated mechanism to actually get these numbers appears later, in "Startup and storage strategy" step 1: "Establish current cold-start and load metrics from authenticated logs or explicit structured startup telemetry."

**Why it matters**: As written, Stage 0's Gate would be satisfied by a script that runs and produces *some* output, even if the cold-start/RSS/latency fields it's supposed to capture remain unverified (exactly the state the Reconciled Baseline already documents today) — because the Gate never requires those specific fields to be non-empty/successfully measured, nor does it reference the authenticated-logs-or-telemetry mechanism at all.

**Recommendation**: Tighten the Stage 0 Gate so its headline deliverable can't pass while unmeasured. Add a bullet requiring cold-start, artifact-load, peak RSS, and first/warm-query + provider latency to be captured as non-placeholder values via one of the two named mechanisms — and specify which mechanism actually applies at Stage 0: for the CURRENT (legacy) baseline only the authenticated-logs path works, because adding structured startup telemetry would modify the running production app and violate the same gate's "current production Space remains unchanged" clause (telemetry can only measure the modernized build). Alternatively, explicitly permit Stage 0 to close with those fields still UNVERIFIED, but then add a hard precondition to the Stage 4/6/7 regression gates that a measured legacy baseline exists before any "no latency/memory regression" or cold-start comparison claim can be made — so the UNVERIFIED status is wired into a gate rather than left in Open Questions #1 / Startup-strategy step 1 (both non-gating sections).

### GATES-05. Stage 5's Gate doesn't enforce its own Action's "multiple cold builds/restarts" requirement

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Stage 5: staging deployment" (Actions vs. Gate)

**Evidence**: Actions: "measure multiple cold builds/restarts rather than a single success;" Gate: "all local and CI gates remain green; staging reports the intended SHA; observable browser/API results meet the oracle; startup and memory fit `cpu-basic`, or a hardware/cost decision is recorded." None of the four Gate bullets requires more than one build/restart to be observed.

**Why it matters**: A single successful staging deploy satisfies every stated Gate bullet, so the plan's own stated goal of not trusting "a single success" for cold-start variance has no enforcement — an implementer under time pressure could legitimately treat one green staging run as passing.

**Recommendation**: Add a Stage 5 Gate bullet that makes the multiplicity requirement checkable, e.g. "at least N (default 3) independent cold-build/restart cycles are recorded, each with cold-start time and pass/fail, and no cycle fails." Also fix the same gap in Stage 0's oracle (define the cycle count so the metric is captured consistently) and consider mirroring it in the Stage 6 production Gate, since the "don't trust a single success" discipline is currently stated only in Stage 5 Actions and enforced by no gate anywhere.

### GATES-06. The staging-Space-ID recording safeguard has no executable gate anywhere

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, sections "Confirmed decisions" (#5) and "Stage 0: baseline and test oracle" (Actions/Gate)

**Evidence**: Confirmed decision #5: "Record its exact ID before creation and verify that exact target before cleanup." Stage 0 Actions includes "decide the exact staging Space ID before creating it;" but Stage 0's Gate ("baseline data and counts are generated by scripts; raw outputs are retained for review; the current production Space remains unchanged") has no bullet checking that the ID was recorded, and neither does Stage 5 (which creates the staging Space) or Stage 6 (which removes it).

**Why it matters**: Low likelihood of harm on its own, but this is precisely the kind of manual pre-creation/pre-deletion safeguard that prevents accidentally operating on the wrong Hub resource — leaving it entirely unenforced means it depends on an implementer remembering a prose instruction under deployment pressure, with no script or checklist artifact to catch a skip.

**Recommendation**: Add gate bullets so the staging-Space-ID safeguard (Confirmed decision #5) is enforced, not merely stated as prose. Because the create call happens in Stage 5 (not Stage 0), place the record-side gate there: Stage 5 Gate bullet — "the decided staging Space ID is recorded in a checked-in file/log before any create/POST call is made, and the created Space's ID matches the recorded value." Optionally add a Stage 0 Gate bullet — "the staging Space ID is decided and recorded." Also strengthen the cleanup side: Stage 6 already gates "staging cleanup is confirmed and recorded," but should add "the deletion target was verified equal to the recorded staging Space ID before removal," since verify-before-cleanup is the operative safety step and currently lives only in Stage 6 Actions, not its Gate.

Likely implied by Stage 5's staging build, but worth a one-line cross-reference rather than leaving it implicit.

Given Stage 0's own metrics may ship UNVERIFIED (see GATES-04), this bullet could end up uncheckable in practice. Not elevated to a full finding because it's downstream of the Stage 0 gap already reported.
- **Central quality gate block is well-formed and stages correctly build on it rather than restate it.** Cross-checked: Stage 1's Gate directly matches the central pytest/ruff/mypy/pre-commit block; Stages 2-6 correctly layer additional checks (browser tests, contract tests, SHA verification) without contradicting or weakening it. No finding here — noted for completeness per the axis's cross-check instruction.
