# RELIABILITY-CICD: Are the plan's CI/CD and observability gates achievable given the CURRENT repo's actual CI setup?

## Assessment

RELIABILITY-CICD verdict: the plan's diagnosis of the CURRENT CI/CD state is directionally accurate but the STAGED FIX never closes the governance gap that makes its own Stage 6 gate meaningful. Confirmed live during this audit: `main` has zero branch protection (`gh api repos/.../branches/main/protection` -> 404 "Branch not protected", re-confirmed independently of the coordinator's pre-audit note) and only three workflows exist in `.github/workflows/`: `hf-space.yml` (push-to-main auto-deploy that is literally just checkout+`git push`, no build-wait/SHA-check/retrieval test), `check-file-size-limit.yml` (a PR-triggered file-size check that, with no branch protection, cannot block a merge), and `bumpver.yml` (a `workflow_dispatch` job that commits and pushes straight to `main`, bypassing any PR entirely). No workflow anywhere invokes pytest/ruff/mypy/pre-commit today, and requirements.txt has no test/lint dev-dependencies — the one existing test (`tests/test_space_build_contract.py`, the regression guard for commit 3e85082) is never run in CI. The plan's Stage 1 action "update GitHub Actions to invoke the complete gate" and Stage 6 gate "merge only after required checks pass" both silently assume a governance/CI mechanism (a workflow that runs the gate pre-merge, and branch protection that makes it required) that does not exist in this repo and is never explicitly scheduled to be created. This is exactly mandate point 3's target: an assumption lacking an executable validation gate. A secondary, previously-unflagged gap: `bumpver.yml`'s direct push to `main` would remain a settings-dependent ungated path straight to public production even after branch protection is added for PRs, since required-status-checks protection normally blocks direct pushes too unless the pushing token has admin/owner bypass — the plan never mentions this workflow at all.

### RELIABILITY-CICD-01. Stage 6's "merge only after required checks pass" has nothing to attach to — no branch protection exists and Stage 1 never commits to creating it

**Severity**: Medium · **Effort**: S · **Location**: docs/modernization-plan.md, section "Stage 6: production rollout" (Actions) and section "Current risks" > "Reliability and observability gaps"

**Evidence**: Plan, Stage 6 Actions: "merge only after required checks pass;". Plan, Reliability section: "The current required PR check only enforces a file-size limit." Live check (re-run this audit, matches coordinator's pre-verified literal): `gh api repos/joshuasundance-swca/govgis_nov2023-slim-faiss/branches/main/protection` returns `{"message":"Branch not protected",...,"status":"404"}`. `.github/workflows/check-file-size-limit.yml:1-14` runs `ActionsDesk/lfs-warning@v2.0` on `pull_request` to `main`, but with zero branch protection it cannot block a merge — it is not "required" in GitHub's binding sense, just a check that runs. Stage 1 Actions ("Stage 1: project foundation") read only: "update pre-commit, Ruff, mypy, pytest, and security checks; update GitHub Actions to invoke the complete gate." — branch protection / required status checks are never mentioned anywhere in the document (grep for "branch protection", "required check", "required status" returns only the Stage 6 phrase itself).

**Why it matters**: As written, Stage 6's gate is unenforceable: a maintainer can merge any PR to `main` today, and after Stage 1, regardless of whether the new quality-gate workflow passes, because GitHub has no required status check configured to block the merge button. Since `.github/workflows/hf-space.yml` auto-deploys on every push to `main`, a merge that skips or fails the gate still auto-deploys to the public production Space. This is a missing technical-enforcement / defense-in-depth layer (accidental or hasty merges are unguarded) rather than a total defeat of the staged design — the plan does document the human "merge only after checks pass" action, it just lacks a mechanism that makes that action mandatory.

**Recommendation**: Add a concrete branch-protection action and gate to the plan so Stage 6's "merge only after required checks pass" has an enforceable mechanism. Two doc changes: (1) In Stage 1 actions (or a new pre-Stage-1 setup action), add: "Configure branch protection on `main` requiring the new CI quality-gate workflow job (and the file-size check) as required status checks; do not allow the requirement to be bypassed." (2) Add to Stage 5 or Stage 6 gate a verifiable check: "`gh api repos/joshuasundance-swca/govgis_nov2023-slim-faiss/branches/main/protection` returns 200 and lists the expected required status checks before executing 'merge only after required checks pass.'" Also tighten the Reliability section line "The current required PR check only enforces a file-size limit" — it is not GitHub-required (merge-blocking) today; state plainly that the file-size workflow merely runs and, with no branch protection, cannot block a merge. Optionally note that on a public repo branch protection is free and that admin-bypass should be disabled so the gate is real rather than aspirational.

### RELIABILITY-CICD-02. bumpver.yml pushes directly to main, bypassing any PR-gated required-check mechanism the plan will add — never mentioned in the document

**Severity**: Medium · **Effort**: S · **Location**: no attachment point in docs/modernization-plan.md today; nearest is "Confirmed decisions" #7 ("Keep production working until a modernized branch passes all local, CI, staging, and live observable gates.") and "Stage 6: production rollout"

**Evidence**: `.github/workflows/bumpver.yml:39-40`: `run: bumpver update --commit --tag-commit --${{ github.event.inputs.bump }} --push`, with `permissions: contents: write` (line 19-20) and checkout using `secrets.WORKFLOW_GIT_ACCESS_TOKEN` (line 25). This commits and pushes directly to `main` on `workflow_dispatch` — not via a PR. `docs/modernization-plan.md` contains zero mentions of `bumpver` (grep for "bumpver", "version bump", "Bump Version" returns no matches).

**Why it matters**: GitHub's required-status-checks branch protection (the fix proposed in finding #1) blocks direct pushes too under normal settings — unless the pushing token/actor has admin or owner bypass (plausible here, since `WORKFLOW_GIT_ACCESS_TOKEN` looks like an owner PAT). So the real, settings-dependent fork is: (i) without bypass, adding branch protection will silently break this workflow (its push gets rejected), or (ii) with bypass, it remains an ungated path straight to `main` that skips pytest/ruff/mypy/the complete gate — and because `hf-space.yml` triggers on every push to `main`, it immediately auto-deploys to the public production Space with none of Stages 1-6's validation. Either way the plan is silent on it.

**Recommendation**: Add a short decision/note to the plan acknowledging `.github/workflows/bumpver.yml`. Frame it around the governance invariant the plan asserts (Stage 6: "merge only after required checks pass"; decision #7's closed local/CI/staging/live-gate loop): today that loop assumes every change reaches `main` via a gated PR, but `bumpver update --commit --tag-commit --push` (bumpver.yml:40, `contents: write`, `WORKFLOW_GIT_ACCESS_TOKEN`) commits, tags, and pushes straight to `main` on `workflow_dispatch`, and because hf-space.yml triggers on any push to `main` (lines 4-5) it immediately redeploys the public production Space. State the settings-dependent fork explicitly rather than assuming one outcome: (i) if the token/actor lacks admin bypass, adding branch protection will REJECT bumpver's push and silently break the version-bump workflow, or (ii) if the token has admin/owner bypass, it stays an ungated path to `main` + auto-deploy. Either outcome argues for the plan to name bumpver explicitly and choose: (a) route version bumps through a PR / disable the direct `--push` and let the deploy workflow fire from the merge, or (b) record a deliberate metadata-only exception, noting it still triggers a production deploy and must be run only against a known-good `main`. This is an S doc edit; branch protection itself is out of scope of this finding (owned by finding #1).

### RELIABILITY-CICD-03. No GitHub Actions workflow currently runs any test tier — Stage 1's "update GitHub Actions to invoke the complete gate" needs to say "create", not "update"

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Stage 1: project foundation" (Actions and Gate)

**Evidence**: Only three workflow files exist in `.github/workflows/`: `hf-space.yml` (push-to-main deploy: checkout + `git push`, nothing else), `check-file-size-limit.yml` (PR file-size check via `ActionsDesk/lfs-warning@v2.0`), and `bumpver.yml` (manual version bump). None of the three invokes pytest, ruff, mypy, or pre-commit. `requirements.txt` (repo root) contains only runtime deps (anthropic, faiss-cpu, huggingface-hub, langchain, langsmith, openai, pydantic, PyYAML, sentence-transformers, torch) — no test/lint dev-dependency file exists. `tests/test_space_build_contract.py` (the regression guard added by recovery commit 3e85082) is never executed by any CI workflow today. Plan text: Stage 1 Gate says "CI logs prove that each expected tier actually ran" but the Action says only "update GitHub Actions to invoke the complete gate."

**Why it matters**: "Update GitHub Actions" presumes an existing workflow close to this purpose; there isn't one. A reader following the plan literally could add a new workflow that mirrors `hf-space.yml`'s trigger (push to main only), which would run the gate AFTER merge, not before — producing a green CI badge on `main` while never having blocked the bad PR, and leaving finding #1's branch-protection fix with no pre-merge job to require. This risk is mitigated by three signals already present elsewhere in the document (the Reliability/observability-gaps diagnosis, the Stage 1 Gate's "CI logs prove each tier ran," and Stage 6's "merge only after required checks pass"), so the likelihood of an implementer actually going wrong here is low — this is a wording/coherence fix, not a missing decision.

**Recommendation**: Two concrete edits: (1) Change the Stage 1 action from "update GitHub Actions to invoke the complete gate" to something like "create a CI workflow (e.g. .github/workflows/ci.yml) triggered on pull_request targeting main (and optionally push to main) that runs pytest, Ruff, mypy, and full pre-commit" — "update" is inaccurate because no existing workflow runs any test tier (hf-space.yml deploys, check-file-size-limit.yml only runs lfs-warning, bumpver.yml only bumps versions). (2) Explicitly connect this new job to the downstream gates: name the pre-merge job as the required status check that Stage 6's "merge only after required checks pass" and the branch-protection finding (#1) rely on — the plan currently never states the CI must be pre-merge/blocking, only that "CI logs prove each tier ran," which a post-merge-only workflow would also technically satisfy.

### RELIABILITY-CICD-04. hf-space.yml's diagnosed false-positive-success defect is never assigned a concrete fix file or mechanism in any stage

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, "Current risks" > "Reliability and observability gaps" vs. "Stage 5: staging deployment" and "Stage 6: production rollout" (Actions)

**Evidence**: Reliability section: "The current deployment workflow reports success when Git push succeeds; it does not wait for the Space build, verify the deployed SHA, or exercise retrieval." — confirmed literally against `.github/workflows/hf-space.yml:1-21`, whose only functional step is `git push https://joshuasundance:$HF_TOKEN@huggingface.co/spaces/... main`. Stage 5 Actions: "deploy the branch; wait for `RUNNING`, verify its SHA, and run retrieval and provider smoke tests;". Stage 6 Actions: "monitor GitHub deployment, HF build, runtime stage, and deployed SHA;". Neither names `hf-space.yml`, nor states whether the wait/verify logic becomes part of that automated workflow (a required check) versus a manual step a human runs separately.

**Why it matters**: Without naming the concrete file/mechanism, the diagnosed fix could be implemented as a one-off manual verification rather than as part of the automated CI signal, so `hf-space.yml`'s "Push to HuggingFace Space" job would keep reporting green even after modernization when the Hub build subsequently fails. Note this does NOT undermine Stage 6's own release gate — Stage 6's gate ("production is `RUNNING` at the merge SHA," line ~405) is an independent observable check, not a read of the push-workflow's self-reported status, and the plan already deems the push proxy insufficient (line 164) and adds independent RUNNING+SHA checks in Stage 5 and Stage 6. The gap is narrower than it first appears: it's that the diagnosed AUTOMATED-signal defect is left unassigned to any concrete mechanism, which is inconsistent with the plan's own insistence elsewhere that CI signals prove what actually ran.

**Recommendation**: Add one clause to Stage 1 (or Stage 5) tying the diagnosed fix to a concrete, automated mechanism, e.g.: "Rewrite `.github/workflows/hf-space.yml` (or add a companion deploy-verify workflow) so that after the push it polls the Space API until `runtime.stage == RUNNING` or a failure/timeout, asserts the returned `sha` equals the pushed commit, and fails the job otherwise — making the deployment workflow's own signal trustworthy rather than a push-success proxy." Frame it as closing the loop on the diagnosed false-positive AUTOMATED signal (not as protecting Stage 6's release gate, which is already independently sound), and optionally note whether that job becomes a required, merge-blocking check once branch protection (finding #1) is added.

### RELIABILITY-CICD-05. Stage 1 modernizes to uv/pyproject but never updates dependabot.yml, which still targets pip/requirements.txt

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md — decision #8 (line 49) and Stage 1 tooling actions (lines 288-293); .github/dependabot.yml

**Evidence**: `.github/dependabot.yml` is `package-ecosystem: "pip"`, `directory: "/"`, grouping `*` — i.e. it watches the current requirements.txt, and has no `github-actions` ecosystem entry at all. Stage 1 replaces that with `pyproject.toml` + uv lockfile + `.python-version` and lists pre-commit/Ruff/mypy/pytest/security + GitHub Actions updates, but grep of the plan for `dependabot` finds only decision #8 ('do not merge PR #45'). The Dependabot config itself — the thing that generated the stale, architecture-mismatched PR #45 the plan warns about — is never scheduled for update to the new ecosystem.

**Why it matters**: After migration, Dependabot keeps operating against the old pip/requirements.txt assumption and won't maintain the uv lockfile — a recurring maintenance-noise and drift source. (Once langchain/requirements.txt are actually removed, Dependabot won't literally re-emit PR-#45 clones; the durable point is that the config still asserts a pip/requirements.txt world post-migration.) Separately, the GitHub Actions workflows Stage 1 updates have no dependabot ecosystem tracking them at all today.

**Recommendation**: Add to Stage 1's tooling actions: "update .github/dependabot.yml for the modernized ecosystem" — point the pip ecosystem at pyproject.toml/uv.lock (Dependabot supports uv within the pip ecosystem) and add a separate `github-actions` ecosystem entry so the workflows Stage 1 updates are actually tracked. Attach a gate: a post-migration Dependabot run opens PRs against the new manifest/lockfile, not the deleted requirements.txt.
