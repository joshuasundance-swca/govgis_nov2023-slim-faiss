# ROLLBACK-OBS: Rollback precision and observable-test strength (mandate point 7)

## Assessment

Both named "Known-good rollback points" (5b3caca, 3e85082) verifiably exist and match their stated descriptions (confirmed via `git show`/`git rev-parse`) — but they are also git-tree-identical, an undisclosed redundancy. The document's structural weakness on this axis is not factual error but specificity: every one of the six per-stage "Rollback" subsections is a prose policy statement ("keep production at its known-good SHA", "stop staging", "redeploy the tagged known-good revision") with zero accompanying git/gh/curl/HF-API command, even though the actual production deploy mechanism (a direct `git push` to the HF Space git remote, bypassing any Hub API) is non-obvious and asymmetric to how staging verification would need to work. SHA verification is likewise stated only as prose ("verify its SHA") despite the coordinator demonstrably having a working, reusable command for exactly that check. Most structurally, Stage 6's gate leans on "the agreed rollback window" as if settled, while the only place a duration is discussed is the unresolved Open Questions section — the load-bearing-open-question pattern the audit brief specifically warns about.

### ROLLBACK-OBS-01. No stage's Rollback subsection contains an executable command; the actual redeploy mechanism (direct git push to the HF Space remote) is never named or disambiguated

**Severity**: Medium · **Effort**: S · **Location**: docs/modernization-plan.md, section "Stage 6: production rollout" (Rollback) and "Stage 5: staging deployment" (Rollback)

**Evidence**: Stage 6 Rollback: "redeploy the tagged known-good revision and verify it reaches `RUNNING` and returns the known-good observable result." Stage 5 Rollback: "stop staging and keep production on `5b3caca`." Neither specifies a git/gh/HF command. The actual deploy path is `.github/workflows/hf-space.yml:17-21`: `git push https://joshuasundance:$HF_TOKEN@huggingface.co/spaces/joshuasundance/govgis_nov2023-slim-faiss main` — a direct push to the HF Space's own git remote, triggered only by a push to GitHub `main`, with no Hub API call involved at all.

**Why it matters**: During an actual production incident on a public Space, whoever executes "redeploy the tagged known-good revision" has two operationally very different options with no guidance: (a) `git revert` the bad commit on GitHub `main` and let the existing workflow re-push (auditable, goes through CI), or (b) push the old SHA directly to the HF Space git remote, bypassing GitHub entirely (faster, but leaves GitHub main and the Space out of sync, and produces no PR/audit trail). Coupled with the confirmed absence of any branch protection on `main` (coordinator-verified-literals.md), either path is currently unconstrained. Stage 5's "stop staging" has the same gap — no huggingface_hub/API/CLI call is named for actually pausing or deleting the staging Space.

**Recommendation**: In the rollback subsections of Stage 5 and Stage 6, replace the strategy-only prose with a concrete command block, and resolve the GitHub-vs-HF-remote ambiguity that the actual deploy path (`hf-space.yml`: direct `git push` of GitHub `main` to the HF Space git remote) creates. Name the GitHub-revert path as the canonical incident procedure — `git revert <bad-sha> && git push origin main`, letting the existing workflow re-push — because it is auditable, goes through CI, and keeps GitHub `main` and the Space in sync. Name the direct force-push to the Space remote (`git push https://<user>:$HF_TOKEN@huggingface.co/spaces/<org>/<space> 5b3caca:main --force`) only as an emergency fallback, and state its cost explicitly: it desyncs GitHub `main` from the Space, so the next merge-triggered workflow run will re-push the bad code. Have Stage 0's existing action ("document the exact rollback command") produce and pin this same block rather than a vague placeholder. Add a staging-teardown command for Stage 5/6 (e.g. `hf repo delete spaces/<org>/<staging-id> --repo-type space -y`; `huggingface-cli` is the legacy alias). Optionally cross-reference the confirmed absence of branch protection on `main`, since it leaves both rollback paths unconstrained.

### ROLLBACK-OBS-02. "Verify its SHA" / "staging reports the intended SHA" are stated as prose gates with no captured command, despite the exact working command already being used to reconcile this document's own baseline

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Stage 5: staging deployment" (Actions, Gate)

**Evidence**: Actions: "wait for `RUNNING`, verify its SHA, and run retrieval and provider smoke tests;" Gate: "staging reports the intended SHA;" No command is given. The "Reconciled baseline" section of this same document was itself produced by querying the Space API (per scratch/coordinator-verified-literals.md: `GET /api/spaces/joshuasundance/govgis_nov2023-slim-faiss` -> `.sha`, `.runtime.stage`) — the exact mechanism the plan needs for this gate already exists and is proven to work, but it isn't written into the plan as the required check.

**Why it matters**: Without the command captured in the plan, Stage 5's gate is unfalsifiable as written — a future implementer (or a different agent picking up the plan) has to independently rediscover the correct API shape, and "verify its SHA" could be satisfied by eyeballing the Space UI instead of a scripted, CI-attachable check. (Verify-pass note: the gate is in fact a clear, falsifiable observable condition whose mechanism the document already demonstrates elsewhere — the defect is that the mechanism isn't captured at the point of use, not that the gate is inherently unfalsifiable.)

**Recommendation**: Capture the proven check as the literal gate command in BOTH Stage 5 and Stage 6 (both currently state SHA verification as prose: "staging reports the intended SHA" / "production is RUNNING at the merge SHA"). Add to each gate a scripted, CI-attachable check, e.g.: `curl -s https://huggingface.co/api/spaces/<org>/<space-id> | jq -r '.sha, .runtime.stage'`, asserting `.sha` equals the expected merge SHA and `.runtime.stage == "RUNNING"` (or the huggingface_hub Python equivalent). This is the same mechanism the plan's own "Reconciled baseline" section already used, and it directly closes the exact gap the plan names at line 162 ("does not... verify the deployed SHA"). Frame it as tightening a clear observable condition into a captured command, not as fixing an "unfalsifiable" gate.

### ROLLBACK-OBS-03. Stage 6's regression gate ("no new security, latency, memory, or provider regression is observed") never references the Stage 0 baseline it needs a comparison basis from

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Stage 6: production rollout" (Gate) vs. section "Stage 0: baseline and test oracle" (Actions)

**Evidence**: Stage 6 Gate: "no new security, latency, memory, or provider regression is observed;" Stage 0 Actions: "capture cold-start, artifact-load, RSS, first-query, warm-query, and provider latency;" — the two are never connected; Stage 6's gate does not say "compared against the Stage 0 baseline" or name a tolerance/threshold.

**Why it matters**: This is the gate that decides whether a live production rollout is left running or rolled back. As written it is a subjective judgment call ("no ... regression is observed") rather than a scripted comparison against the numbers Stage 0 was explicitly built to capture, so two operators could reach opposite rollback decisions from the same data. The plan otherwise names a comparison basis consistently — "the agreed threshold" (Stage 2), "the predeclared quality floor" (Stage 7) — making this gate's silence on basis and tolerance an internal inconsistency rather than a one-off gap.

**Recommendation**: Rewrite the Stage 6 gate line (docs/modernization-plan.md:407) to name a comparison basis and a tolerance, matching the plan's own threshold-naming discipline used at Stage 2 ("the agreed threshold", L321) and Stage 7 ("the predeclared quality floor", L429). Anchor the comparison to the Stage 5 staging measurements of the SAME modernized build (L380 already measures multiple cold builds/restarts), NOT to the Stage 0 baseline — Stage 0 measures the legacy Streamlit app and the plan explicitly targets "measured startup improvements" (L19), so a strict +X%-of-legacy bound would wrongly penalize the intended cold-start gain. Suggested wording: "latency, memory, and error rate stay within [agreed tolerance] of the Stage 5 staging measurements recorded for the same query set and build; any provider failure resolves through the Stage 4 sanitized-error path (retrieval survives), never an unhandled exception." If the tolerance is not picked now, add it to the Open implementation-time questions list (alongside the rollback-window question at L517), since the regression threshold is currently load-bearing at the production gate but not surfaced as an open question.
