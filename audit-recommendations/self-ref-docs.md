### SELF-REF-DOCS-01. Stage 6's "merge only after required checks pass" gate has no corresponding action anywhere in the plan to actually create required checks

**Severity**: Medium · **Effort**: S · **Location**: `docs/modernization-plan.md`, "Stage 6: production rollout" (Actions, line 396), cross-referenced with "Current risks" / "Reliability and observability gaps" (lines 159–164)

**Evidence**: Stage 6 Actions state: "merge only after required checks pass" (line 396). "Reliability and observability gaps" already documents the underlying gap: "The current deployment workflow reports success when Git push succeeds; it does not wait for the Space build, verify the deployed SHA, or exercise retrieval. The current required PR check only enforces a file-size limit." (lines 161–164). Live-verified: `gh api repos/.../branches/main/protection` returns 404 "Branch not protected" — `main` has zero GitHub branch protection today, so nothing on GitHub is actually "required" in the sense that would block a merge. Scanning all 8 stages (Stage 0 through Stage 7) for any action item that configures branch protection or required status checks on GitHub returns nothing: Stage 1's "update GitHub Actions to invoke the complete gate" (line 293) only touches workflow *definitions*, not the separate GitHub branch-protection setting that makes a check actually block a merge. `.github/workflows/hf-space.yml` auto-deploys to the public Space on every push to `main` via a bare `git push`, with no build/SHA/retrieval verification. `.github/workflows/check-file-size-limit.yml` is the sole PR check today and, absent required-check configuration, cannot block anything.

**Why it matters**: As written, Stage 6 can be executed to the letter while its own precondition is vacuously true: with no required status check configured, there is nothing on GitHub that would prevent merging a modernized branch into `main` with red CI, and `main` auto-deploys straight to the public HF Space on every push. The staged safety plan's central production gate has no teeth unless this is fixed before Stage 6 is reached.

**Recommendation**: Add an explicit action item so Stage 6's "merge only after required checks pass" has an enforcement mechanism, not just a process instruction. Best placed at the end of Stage 1 (once the CI gate exists) or as a Stage 6 pre-merge bullet: "configure GitHub branch protection on `main` requiring the Stage 1 CI workflow(s) (pytest/ruff/mypy/pre-commit) — and, once it exists, the browser/staging smoke workflow — as required status checks." Add a matching Stage 6 gate line confirming branch protection is active before the modernized merge. Important refinement: because this is a solo-owned repo, standard branch protection does not block the owner/admin from merging unless "Do not allow bypassing the above settings" (enforce for administrators) is also enabled — the action item must call that out explicitly, or the protection will have no teeth against the only actor who can merge. This can also be applied immediately as a standalone, reversible repo-settings change independent of the doc edit (grade that standalone action S).

### SELF-REF-DOCS-02. The 2026-07-20 baseline snapshot is treated as durable but has no re-reconciliation gate at Stage 0 kickoff, though main is not frozen

**Severity**: Low · **Effort**: S · **Location**: `docs/modernization-plan.md` — "Reconciled baseline" / "Verified on 2026-07-20" (lines 52–66), rollback pins to `5b3caca` (lines 5, 68–75, 390, 411–413); Stage 0 (lines 267–282)

**Evidence**: Every baseline fact and rollback target is pinned to `5b3caca` "Verified on 2026-07-20" — the same day the Codex handoff and this audit ran, with "implementation has not begun." Nothing re-confirms the live baseline still equals `5b3caca` when Stage 0 actually starts, yet `main` is demonstrably not frozen: `bumpver.yml` (lines 39–40) pushes a commit and tag directly to `main` on manual `workflow_dispatch`, and Dependabot PR #45 is confirmed open. Decisions #7/#8 and all rollback steps assume `5b3caca` is the current production SHA. Live-reverified during this axis's own pass: `origin/main` and GitHub `main` are both still `5b3cacaf27fc4c75cb4e6e4c3d86dc1796ece5c9` (unchanged since the plan was written), and PR #45 remains open — so the specific snapshot has not yet gone stale, but nothing in the plan would catch it if it did before Stage 0 begins.

**Why it matters**: If any push (a version bump, a merged Dependabot PR) lands on `main` between plan-writing and Stage 0, the "known-good rollback point" and "keep production working" guarantees silently reference a superseded SHA, and rollback could restore the wrong revision on a public service. Mitigating factors that keep this at low rather than medium: Stage 0 already includes "tag the known-good release and document the exact rollback command" (line 275) as partial protection; `main` only moves via deliberate human action here, not automatically; and the worst-case harm is rolling back to a superseded-but-still-`RUNNING` revision — an operational regression, not a security or data-loss event.

**Recommendation**: Add an explicit Stage 0 gate that re-runs the baseline reconciliation (git/gh/Space-API) and asserts the live production SHA still equals the recorded baseline `5b3caca` before any modernization work begins; if it has moved, update the recorded baseline AND every hard-coded `5b3caca` rollback reference (lines 5, 71, 390, 412–413), since the existing "tag the known-good release" action (line 275) neither asserts equality nor rewrites those literals. Reword the "Reconciled baseline" header (lines 52–54) to state the snapshot is time-stamped and must be re-validated at Stage 0 kickoff, not treated as durable. Note in the diff that this directly serves review-mandate point #7 (strengthen rollback).
