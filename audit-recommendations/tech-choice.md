# TECH-CHOICE: Are Gradio / Python 3.14 / uv / direct provider clients / the artifact split / HF OAuth still the smallest reliable choices?

## Assessment

Per-choice verdicts (mandate point 4), each checked against live official docs/PyPI fetched 2026-07-20:

- Gradio (vs Streamlit / vs static+API split): HOLDS. Streamlit is absent from the current documented valid `sdk` values (`gradio`, `docker`, `static` — spaces-config-reference) and app.py's `st.components.v1.html(...)` raw-HTML injection (app.py:225,227) is a live XSS path the plan already targets. A static-Space alternative is disqualified by live docs (no server Python runtime; secrets/variables exposed client-side) but the plan never records that reasoning — finding #3 (low).
- Python 3.14 (vs 3.12/3.13): HOLDS. Confirmed live: torch 2.13.0 ships cp314 Linux wheels, faiss-cpu 1.14.3 ships a forward-compatible cp310-abi3 Linux wheel, Python 3.14.6 is a mature sixth maintenance release. The plan correctly treats full compatibility as an executable Stage 1 gate rather than an assumed fact — no revision needed.
- uv (vs plain pip/pyproject): PARTIALLY HOLDS WITH A GAP. uv remains sound for local/CI dependency management and matches this fleet's own new-code convention, but the plan never documents how the uv-locked pyproject.toml is supposed to reach the actual Gradio Space build mechanism, which — per two independently fetched live doc pages — only ever reads `requirements.txt`/`pre-requirements.txt`/`packages.txt`, with Python/Gradio/OAuth version entirely controlled by README YAML front matter the plan never mentions updating. This is the highest-impact finding (#1, medium) and touches three of the mandate's six tech choices at once (Gradio SDK, Python 3.14, uv, and HF OAuth all land through the same unaddressed README/requirements.txt surface).
- Direct provider SDKs replacing LangChain: HOLDS, proportionate to app.py's actual (thin) LangChain usage — see minor notes.
- Safe FAISS/parquet artifact split: HOLDS, remains the smallest reliable fix for the plan's own stated critical trust boundary.
- HF OAuth inference-api (vs BYOK-only scope cut): the decision itself is not re-litigated (already narrowly scoped, already gated in Stage 4), but its concrete implementation mechanism (`hf_oauth: true` README field, Gradio's built-in login support) is unaddressed by the plan in the same way as the uv/requirements.txt gap — folded into finding #1 rather than a separate item.

Additional mandate check (module list vs flow diagram): mostly 1:1, but the flow diagram's central sequencing step has no owning module given app.py's narrow "event wiring only" scope — finding #2 (low).

No churn was manufactured: three of the six named tech choices (Gradio, Python 3.14, provider-SDK/LangChain removal, artifact split — four, really) verified clean against live docs/PyPI with no plan changes recommended for the choice itself.

### TECH-CHOICE-01. uv/pyproject.toml decision has no documented path into the actual Gradio Space build contract — README YAML front matter is never addressed

**Severity**: medium · **Effort**: S · **Location**: docs/modernization-plan.md, sections "Confirmed decisions" (items 1 and 6) and "Stage 1: project foundation"

**Evidence**: Confirmed decisions #1: "Migrate the UI from the deprecated built-in Streamlit Space SDK to the native Gradio Space SDK." Confirmed decisions #6: "Modernize the Python project and dependency workflow according to current Hugging Face and repository standards. The recommended target is Python 3.14 with a `pyproject.toml` and a locked uv environment, subject to a clean Linux install and Hugging Face staging build." Stage 1 Actions: "add `pyproject.toml`, package layout, lockfile, and `.python-version`;" Stage 1 Gate: "fresh locked install succeeds; `pytest`, Ruff, mypy, and full pre-commit are green; CI logs prove that each expected tier actually ran."

A whole-document grep for the literal strings "requirements.txt", "python_version", "sdk_version", and "hf_oauth" returns zero matches anywhere in the plan. Live official docs fetched 2026-07-20 contradict the plan's implicit assumption: spaces-dependencies states "If you need other Python packages to run your app, add them to a requirements.txt file at the root of the repository... You can also add a pre-requirements.txt file" — pyproject.toml/uv.lock are never mentioned as Space build inputs. spaces-config-reference states the Space's Python version is set only via "`python_version`: _string_ ... Defaults to `3.10`" in the README YAML, with no mention of `.python-version`. spaces-oauth states "All you need to do is add `hf_oauth: true` to your Space's metadata inside your `README.md` file" (plus `hf_oauth_scopes: [inference-api]`) — the mechanism for the plan's own Confirmed decision #4 (HF OAuth) is likewise never named in the plan. The current README.md front matter (sdk: streamlit, sdk_version: 1.29.0, python_version: 3.11) is also never flagged for update anywhere in the staged actions. The repository already has `tests/test_space_build_contract.py`, which asserts README python_version/sdk_version and requirements.txt contents against the current Streamlit/3.11 values — the plan never references this existing test.

**Why it matters**: As written, Stage 1's gate only validates the local/CI uv environment. Nothing in the plan generates, exports, or checks a requirements.txt (or pre-requirements.txt) derived from the uv lockfile, and nothing updates the README YAML fields (sdk, sdk_version, python_version, hf_oauth, hf_oauth_scopes) that are the sole mechanism the live Gradio Space build actually reads. A maintainer following the plan literally could pass every Stage 1 gate locally and in CI while the deployed Space either fails to build (no requirements.txt present), silently installs from a stale/hand-written requirements.txt that has drifted from the lockfile, or never gains the OAuth capability Confirmed decision #4 promises. Severity is medium rather than high: Stage 5 staging is explicitly designed to catch build failures before production (bounding blast radius to a burned staging cycle), and part of the gap is self-forcing — the Gradio SDK change is required for the app to run at all, and the repo already has `tests/test_space_build_contract.py` coupling README front matter to requirements.txt, which a maintainer following the plan would hit directly. The residual risk that keeps this above low is quieter: lockfile-to-requirements.txt version drift that still builds cleanly from stale pins would not be caught by either of those forcing functions.

**Recommendation**: Keep the two-part fix, with refinements: (a) Add a Stage 1 action + gate to generate requirements.txt from the uv lockfile (e.g. `uv export --format requirements-txt`) as the Space build artifact, plus a CI drift check that fails if the committed requirements.txt diverges from the lockfile — this closes the tested-lockfile vs deployed-requirements.txt reproducibility gap, the one failure mode staging may not catch. (b) Make README YAML front-matter updates explicit stage actions AND gate items, sequenced correctly: `python_version: "3.14"` at Stage 1, `sdk: gradio` + `sdk_version` at Stage 3 (when the Gradio app actually exists), and `hf_oauth: true` + `hf_oauth_scopes: [inference-api]` at Stage 4. (c) Additionally, name the existing `tests/test_space_build_contract.py` in Stage 1/3 actions — it already asserts README python_version/sdk_version and requirements.txt contents against the current Streamlit/3.11 values and will fail (or falsely pass on stale values) unless deliberately rewritten for the Gradio/3.14 contract; the plan never references it.

### TECH-CHOICE-02. Target-architecture flow diagram has a pipeline-orchestration step with no owning module, while app.py is explicitly scoped to UI wiring only

**Severity**: low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Target architecture"

**Evidence**: The flow diagram reads: "Gradio UI -> validated search request -> embedding + FAISS retrieval -> typed GIS search results -> optional provider-neutral query rewrite or answer synthesis -> safe presentation model -> sanitized rendered output". The module list immediately below assigns: "`app.py`: Gradio composition and event wiring only." ... "`govgis/retrieval.py`: query embedding and direct FAISS search." ... "`govgis/providers/base.py`: narrow provider protocol and common errors." ... "`govgis/presentation.py`: plain-text conversion, link validation, and escaped Markdown." No module is named for sequencing retrieval -> optional provider call -> presentation, or for the branching/fallback logic the plan itself later requires: Stage 4's gate states "retrieval survives every provider failure" — that is orchestration behavior, not UI wiring, retrieval, a provider, or presentation. This is not a documented-and-justified decision being re-litigated; the plan simply never places orchestration anywhere.

**Why it matters**: If app.py stays limited to "composition and event wiring only" as stated, the per-request glue code (call retrieval, decide whether to call a provider, catch provider failures and still render retrieved results, build the presentation model) has no designated home. In practice it would end up inside app.py's event handlers anyway, contradicting the module's stated scope. Severity is low: the fallback behavior and its executable gate already exist in the plan (Stage 4 gate, and line 208's "show records even if synthesis fails"); this is a naming/placement clarity revision in a planning document, not a missing requirement, security hole, or a conflict with live reality.

**Recommendation**: Add one module to the list, e.g. `govgis/search.py` (or `pipeline.py`): "orchestrates retrieval, optional provider rewrite/synthesis with fallback to retrieval-only on provider failure, and presentation-model assembly for a single request," and narrow app.py to "Gradio composition and event wiring that delegates to `govgis/search.py`." Lead the rationale with architectural clarity (the flow diagram's orchestration step + the Stage 4 "retrieval survives every provider failure" gate + line 208's "show records even if synthesis fails" have no owning module while app.py is scoped to "wiring only"), and give the fallback guarantee a concrete unit under fast test. Note: Gradio handler functions written as plain Python (`.click(fn=...)`) are directly unit-testable without a browser, so the case for this module should rest on architectural clarity and testability of the fallback guarantee, not on a claim that Gradio handlers can only be exercised through browser/API smoke tests.

## Minor notes (not adversarially verified)

- **Python 3.14 wheel-availability risk is real but already correctly gated, not asserted.** Live PyPI checks (2026-07-20) confirm torch 2.13.0 ships cp314 manylinux_x86_64 wheels and faiss-cpu 1.14.3 ships a cp310-abi3 (forward-compatible) manylinux wheel, so the binary-wheel risk the plan calls out in Stage 1 ("validate binary wheels on the same Linux/Python combination used by the Space") is well-founded caution rather than a live blocker. sentence-transformers 5.6.0's PyPI classifiers list only up to Python 3.13 (no 3.14 classifier yet) despite declaring `Requires-Python >=3.10` with no upper bound; since it is pure-Python this is unlikely to block installation but is worth a one-line note if Stage 1's wheel-validation gate surfaces anything. Verdict: Python 3.14 remains the smallest reliable choice as scoped — the plan already treats this as an executable gate (Stage 1) rather than a stated fact, which is the correct posture; no plan revision needed.
- **Direct provider SDKs replacing LangChain — verdict holds, proportionate.** app.py's actual LangChain usage (app.py:8-13, 60-99, 135-169) is a thin LCEL chain wrapping a `HuggingFaceBgeEmbeddings` embedder, a `FAISS` vectorstore/retriever, and two `ChatAnthropic` calls behind two prompt templates — no LangChain-specific feature (tools, agents, memory, callbacks) is in use. Direct Anthropic/OpenAI clients are a strict complexity reduction for this shape, and removing LangChain also eliminates the FAISS pickle-deserialization surface the plan itself calls its "Critical trust boundary." No revision needed.
- **FAISS index + typed parquet/JSONL artifact split — verdict holds.** Given the stated goal (eliminate a Hub-hosted pickle-bearing blob from the runtime trust path) and the single small cpu-basic Space's constraints (no persistent storage, 16GB RAM), a native `index.faiss` plus checksummed, versioned parquet/JSONL metadata remains the smallest reliable choice versus either keeping the LangChain FAISS wrapper or standing up an external vector-DB service this app doesn't need. No revision needed.
- **HF OAuth inference-api scope — decision itself not re-litigated.** Confirmed decisions #3/#4 already scope this narrowly (curated models only, least-privilege `inference-api` scope) and Stage 4 already carries a gate ("HF calls are attributed to the signed-in user, not the Space owner"), so per the audit's constitution rule this doesn't qualify as a standalone finding. The concrete implementation gap — that the plan never names the `hf_oauth: true`/`hf_oauth_scopes` README fields or Gradio's built-in OAuth login support that the decision depends on — is folded into finding #1 above rather than reported separately.
