# TRUST-BOUNDARY: Depth of the three named security risks plus secrets/cost/abuse

## Assessment

TRUST-BOUNDARY axis: the plan's three named risks (FAISS deserialization, unsafe rendering, prompt injection) are each substantively addressed with real mitigations, and two of the deep-dive's specific worries (a Gradio target explicitly forbidding `gr.HTML` for untrusted content; model output named as untrusted alongside dataset content) turned out to already be correctly written into the document — not findings. The genuine gaps cluster around durability and closure rather than initial design: (1) the plan's own rollback mechanism, exercised at every stage, silently restores the exact two of three named critical risks (confirmed against live app.py: `FAISS.deserialize_from_bytes` at app.py:94-98, raw `st.components.v1.html` at app.py:225,227) without ever saying so; (2) the link-validation/scheme-allowlist protection is described for structured dataset records but is never explicitly re-asserted against freeform LLM-generated markdown once Stage 4 adds LLM synthesis — exactly the render-loop the mandate asked about; (3) and (4) two of the plan's own listed mitigations (timeout/retry/concurrency bounds, and the BYOK never-in-logs policy) are aspirational policy statements with zero numbers and zero executable gates anywhere across 8 stages, both squarely mandate-point-3 territory. Two further gaps are lower-stakes gate-completeness items (no evidence gate for the no-network conversion claim; no durable static check against `gr.HTML` regression). All six findings propose S-effort document edits (added gate bullets or a sentence of risk disclosure), consistent with auditing a planning document rather than software.

### TRUST-BOUNDARY-01. BYOK "never enter logs/caches/telemetry/exceptions" policy has no stated verification mechanism

**Severity**: High · **Effort**: S · **Location**: docs/modernization-plan.md, "Confirmed decisions" item 2, and "Stage 4: providers and authentication" (Actions/Gate)

**Evidence**: "Use BYOK for Anthropic and OpenAI. Keys must remain session-scoped and must never enter logs, caches, telemetry, URLs, persisted state, or exception messages." Stage 4 Actions say only "sanitize exceptions and instrument latency/usage without secrets" (an action, not a gate); Stage 4 Gate's closest language is "opt-in live smoke tests pass without exposing credentials," which does not specify what is checked or how exposure would be detected. `.pre-commit-config.yaml` has no secret-scanning/log-scrubbing hook today (only `detect-private-key`, which targets committed key files, not runtime log/telemetry leakage), and Stage 1's "update pre-commit ... and security checks" does not name adding one.

**Why it matters**: A security-critical claim about public-facing BYOK key handling rests entirely on developer discipline, with no automated or manual check anywhere across the 8 stages. A future logging statement, an exception handler that captures a request object, or a telemetry payload that includes headers could leak a user's Anthropic/OpenAI key with nothing in CI or the gates catching it.

**Recommendation**: Add an explicit, observable Stage 4 gate that operationalizes Confirmed decision 2's non-leakage rule, e.g.: "A test exercises every provider client's success and error paths with a synthetic non-secret sentinel substituted for the API key, captures all logs, exception messages/tracebacks, and telemetry/usage payloads emitted during the run, and asserts the sentinel never appears in any captured output." Tie it explicitly to the existing "sanitize exceptions and instrument latency/usage without secrets" action so the action has a gate. Keep the detect-secrets suggestion for Stage 1 as optional and label its scope precisely: it guards committed secrets, not runtime log/telemetry leakage, so it complements but does not replace the sentinel test. Optionally clarify the existing "opt-in live smoke tests pass without exposing credentials" bullet to reference this deterministic mocked/recorded test as the mechanism, since a passing live smoke test alone does not detect a leak.

### TRUST-BOUNDARY-02. http/https link-scheme allowlist and "unsafe links do not execute" gate are never re-verified against LLM-generated answer text

**Severity**: Medium · **Effort**: S · **Location**: docs/modernization-plan.md, sections "Unsafe rendering", "Prompt injection", "Stage 3: Gradio and secure presentation" (Gate), "Stage 4: providers and authentication" (Gate)

**Evidence**: Target policy under Unsafe rendering: "parse records into strict Pydantic v2 models; accept external links only with `http` or `https` schemes ... convert source HTML descriptions to plain text ... do not use `gr.HTML` for dataset, user, or model-controlled content." Prompt injection section says only "output rendering and link validation still apply" with no restated test. Stage 3's Gate ("browser-level tests prove scripts and unsafe links do not execute") runs while Stage 3 explicitly "retain[s] retrieval-only operation" (no LLM yet). Stage 4's Gate, added after LLM synthesis lands, lists only: "provider contract tests pass with recorded fixtures or mocks; opt-in live smoke tests pass without exposing credentials; retrieval survives every provider failure; HF calls are attributed to the signed-in user, not the Space owner" — no unsafe-link/script-execution re-test against LLM output appears anywhere.

**Why it matters**: This is precisely the closed-loop risk named in the review mandate: retrieved metadata is untrusted and fed to an LLM (Prompt injection section), and the LLM's output is then rendered back through the same presentation layer. The http/https scheme allowlist is described in the context of parsing structured Pydantic record fields, not unstructured LLM prose containing embedded markdown links. Nothing in the staged gates confirms a prompt-injected record that causes the model to emit a `javascript:`/`data:` URI markdown link is caught before rendering.

**Recommendation**: Add an explicit Stage 4 gate item: "re-run the Stage 3 browser-level unsafe-link/script-execution test against LLM-synthesized answers, including a fixture where a prompt-injected record causes the model to emit a `javascript:`/`data:` URI markdown link; assert the presentation layer strips, neutralizes, or refuses to render it as a live link." In the "Unsafe rendering" section, clarify that `govgis/presentation.py`'s sanitization applies uniformly to structured record URL fields AND to freeform LLM-generated markdown prose — noting both mechanisms in play (the http/https scheme allowlist for structured URL fields, and Markdown escaping / `sanitize_html` for generated prose) so an implementer does not assume one path is covered by the other. Keep this framed as tightening an already-stated policy (lines 128 and 145 already declare model output untrusted and link validation applicable), not as a newly discovered hole.

### TRUST-BOUNDARY-03. Timeout/retry/concurrency mitigations are stated with no numbers and no executable gate

**Severity**: Medium · **Effort**: S · **Location**: docs/modernization-plan.md, section "Secrets, cost, and public abuse" and "Stage 4: providers and authentication" (Gate)

**Evidence**: "Add bounded timeouts, retries only for transient failures, concurrency limits, and user-visible rate/cost guidance." No numeric value for any of these appears anywhere in the document. Stage 4's Gate lists only: "provider contract tests pass with recorded fixtures or mocks; opt-in live smoke tests pass without exposing credentials; retrieval survives every provider failure; HF calls are attributed to the signed-in user, not the Space owner" — none of these test a timeout ceiling, retry cap, or concurrency limit.

**Why it matters**: As written, a Stage 4 implementation could ship an unbounded or arbitrarily chosen timeout/retry/concurrency policy and technically satisfy every listed gate, since none of the gates test bound enforcement. On a public, anonymous, BYOK-optional Space this leaves a host-availability exposure with nothing checkable to gate on: retrieval-only requests need no key at all, so unbounded concurrency here is not a provider-cost problem, it is a resource-exhaustion problem against the free `cpu-basic` instance. Because line 152 forbids owner-funded keys and the HF lane is attributed to the signed-in user, unbounded retries on the provider path burn the user's own BYOK key/OAuth quota, not the owner's budget — so the primary owner-facing exposure is host availability (DoS of `cpu-basic`), with user-key protection secondary.

**Recommendation**: In the "Secrets, cost, and public abuse" section, replace the un-numbered mitigation with concrete placeholder values to be finalized during measurement (matching how the plan already defers model defaults and query counts): provider request timeout <=30s; <=2 retries on 5xx/timeout only, never on 4xx; a stated max concurrent in-flight provider calls per session and per Space instance; and a rate limit on retrieval-only requests scoped independently since they require no key. Then add executable gate items, split by stage: the retrieval-only concurrency/rate-limit gate belongs in STAGE 3 (the Gradio retrieval app ships there, before any provider exists, so the anonymous-DoS vector on `cpu-basic` is live at Stage 3, not Stage 4) — assert a load test confirms requests beyond the stated concurrency limit are throttled rather than silently unbounded. The provider timeout/retry/concurrency gate belongs in STAGE 4 — assert a test aborts a provider call that exceeds the stated timeout and that retries fire only on the allowed transient classes.

### TRUST-BOUNDARY-04. Rollback silently reopens the two other named critical trust-boundary risks

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Known-good rollback points" and Stage 2/6 "Rollback" subsections

**Evidence**: "Known-good rollback points: GitHub and Space revision: `5b3cacaf27fc4c75cb4e6e4c3d86dc1796ece5c9` ... Existing runtime contract: Python 3.11 and Streamlit 1.29.0". Stage 6 Rollback: "redeploy the tagged known-good revision and verify it reaches `RUNNING` and returns the known-good observable result." The redeployed revision is the current app.py, confirmed at app.py:94-98 to call `FAISS.deserialize_from_bytes(... serialized=infile.read())` (the exact pickle-like deserialization named "Critical trust boundary" elsewhere in this same document) and at app.py:225,227 to call `st.components.v1.html(data.get("description"...))` / `st.components.v1.html(data.get("parent_service_description"...))` on unsanitized dataset text (the exact "Unsafe rendering" XSS path named elsewhere in this same document).

**Why it matters**: Every stage's rollback plan, including the emergency Stage 6 rollback, is "redeploy the legacy production revision." The plan never states that doing so restores the exact pickle-deserialization and raw-HTML-XSS exposure it labels "Critical" and treats as risks to close. An on-call maintainer invoking the documented rollback command during an incident would reasonably read "known-good" as risk-neutral, when it is actually a return to two of the three named trust-boundary risks on the public Space, for however long the rollback window stays open. Note this is a documentation-completeness gap, not a novel hazard: rollback re-establishes the current accepted public baseline (the legacy app with both risks is live today and has been for the Space's whole life), and Stages 1-5 rollbacks explicitly keep legacy production untouched ("keep production on 5b3caca") — those are status-quo holds, not reopenings, since nothing was closed to reopen. Only Stage 6 (post-cutover) is a true reopening.

**Recommendation**: Add one sentence to "Known-good rollback points" and to Stage 6's Rollback subsection (only) stating that redeploying the legacy `5b3caca` revision restores the LangChain/pickle-like FAISS deserialization (app.py:94-98) and the raw-HTML rendering path (app.py:225,227) documented under "Current risks," and that any Stage 6 rollback held open beyond the stated observation window should be tracked as an accepted, time-boxed residual-risk period. Do NOT add this to Stages 1-5. Frame the note as clarity for incident responders, since the legacy risks are the current accepted live baseline, not novel exposure the rollback introduces.

### TRUST-BOUNDARY-05. No gate verifies the FAISS conversion actually ran isolated/no-network

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Critical trust boundary: serialized FAISS data" and "Stage 2: safe artifact conversion and retrieval core" (Gate)

**Evidence**: "Run conversion in an isolated, no-network process, then validate vector/document counts and retrieval parity." Stage 2 Gate: "no pickle or dangerous-deserialization path is reachable; vector count equals metadata count through a script; baseline retrieval quality meets the agreed threshold; corrupt or mismatched artifacts fail closed with a useful message." None of these confirm the conversion process itself ran without network access.

**Why it matters**: The "isolated, no-network" requirement exists specifically to contain the highest-risk moment in the entire plan — the one place the old pickle-like format is still deserialized at all — against exfiltration or second-stage payload fetch. Without a gate proving isolation was enforced, this mitigation is a written intention with nothing checking it happened. This is a build-time, developer-only operation (anonymous public users are never exposed to it, and the runtime deserialization path is separately gated), and the artifact is the maintainer's own, checksum-verified against its own Hub upload, so this is a defense-in-depth gap rather than a live public-facing hole.

**Recommendation**: Add a Stage 2 Gate item that requires evidence the one-time legacy-artifact conversion ran without outbound network access, e.g.: "the conversion is executed in a network-egress-disabled sandbox (a Linux network namespace / firewalled run, or a CI job with egress blocked) and a log or attestation confirming no outbound calls occurred during deserialization of the legacy artifact is retained for review." Do NOT hard-mandate a GitHub-hosted CI runner: the legacy FAISS artifact is ~4.0 GiB and loading the pickle+docstore can exceed a standard runner's ~7 GB RAM / ~14 GB disk; keep CI as one example, not the required venue.

### TRUST-BOUNDARY-06. "Do not use gr.HTML for untrusted content" has only a one-time browser test, no durable regression gate

**Severity**: Low · **Effort**: S · **Location**: docs/modernization-plan.md, section "Unsafe rendering" (Target policy) and "Stage 3: Gradio and secure presentation" (Gate)

**Evidence**: "do not use `gr.HTML` for dataset, user, or model-controlled content;" Stage 3 Gate: "browser-level tests prove scripts and unsafe links do not execute; local Gradio API and browser smoke tests pass; required GIS fields and links are visible and usable." No lint/static/grep gate against `gr.HTML` usage appears anywhere in the document.

**Why it matters**: This design decision is already correct and not itself in question — it already has an executable gate (the Stage 3 dynamic browser test) and multiple layered mitigations (Pydantic parsing, plain-text conversion, escaped Markdown). But per the review mandate's point on executable validation gates, it currently has only an expensive, one-time Stage 3 dynamic browser test enforcing it. A later change (e.g., a Stage 7 footprint-reduction refactor, or an unrelated future feature) could reintroduce `gr.HTML` for a new field with no CI signal unless a browser test happens to cover that exact new field.

**Recommendation**: In Stage 1 (which already says "update ... security checks" and whose pre-commit config already ships bandit) or the Central quality gate, add one cheap permanent static rule scanning `govgis/` and `app.py` for `gr.HTML(`/`gradio.HTML(` that fails the build on any hit, so the written "do not use gr.HTML for untrusted content" policy is enforced on every commit rather than only at the one-time Stage 3 browser test. Frame it explicitly as complementary to (not a replacement for) the Stage 3 adversarial browser fixtures, and note the grep only enforces the specific gr.HTML rule — the broader XSS surface (e.g. Markdown with sanitize_html=False, DataFrame datatype="html") still relies on the browser tests and Pydantic/plain-text pipeline.
